# Preserve Borealis/NanoVG, optimize OunceVK/Zink first, and keep native Vulkan evaluation gated

The port preserves Borealis/NanoVG, upstream XML layouts, resources, focus behavior, and MPVCore rather than rewriting the application UI from scratch or replacing the player framework. Its canonical initial production rendering stack is Vulkan-backed:

`Borealis / NanoVG + libmpv -> SDL2 / EGL / OpenGL ES 3.1 -> OunceVK Zink -> NVK Vulkan -> Switch 2 GPU`

OpenGL ES 3 is the one production rendering configuration (`USE_GLES3=ON`, `USE_GLES2=OFF` in the `switch2-release` preset): an ES 3.1 context from OunceVK's EGL, Borealis' NanoVG GLES3 backend and MPVCore's `#version 300 es` composition shaders, all existing upstream paths. GLES2 had been picked only to reproduce KaiTube's baseline; neither the console nor OunceVK requires it, and Zink documents ES 3.1. The GLES2 context remains buildable (`-DUSE_GLES2=ON`) only for the one-off hardware comparison in `#23`. That ticket ends with a single configuration: GLES3 adopted and the GLES2 branches deleted, or, if the device shows a concrete GLES3 blocker, GLES2 replacing GLES3 rather than running beside it.

We optimize copies, texture uploads, synchronization, thumbnail loading, danmaku batching, and presentation frame scheduling on this stack first, and only where a recorded device profile shows the cost. Preserving Borealis and keeping rendering distinct from libounce VideoDecoder hardware decoding does not categorically prohibit evaluating a native Vulkan backend under existing Borealis/NanoVG and libmpv/libplacebo seams: native Vulkan is evaluated on an isolated post-G2 research branch against the optimized Zink baseline and adopted only if measured gains justify its maintenance cost without permanently maintaining competing production renderers or a large private libmpv fork.
